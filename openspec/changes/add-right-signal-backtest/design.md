## Context

当前 React 页面通过 `getSignalReport(ticker)` 调用 Python API，后端 `build_signal_report(ticker)` 总是拉取最新日线并以最后一根 K 线作为分析截面。右侧趋势确认度、阶段、右侧 4 态状态和图表都只能解释“今天”，无法回答“在历史某一天，当时系统会怎么判断”。

`stock-signal-analyzer` 的设计文档已把回测验证列为后续可加项。本次变更补这个验证缺口，但产品定位不是完整系统化交易回测，而是“A 为主 + 折线图当证伪镜”：复用同一套信号公式和阶段规则，在指定日期只使用当时已经可见的数据计算结论；再把默认近 60 个交易日的右侧确认度、归一化价格和轻量前瞻结果标签沉淀成趋势序列，帮助用户判断这套自由量价框架是否滞后、失真或过度自信。

约束：

- 不能改变既有 11 个信号公式的语义，避免同时调整规则和验证工具导致结果不可归因。
- 历史复盘必须避免未来数据泄漏，尤其是日线截断、指数环境、成交密集区和 quote 展示。
- 前瞻结果标签只能用于证伪和校准，不能反向进入 as-of 当天的信号、阶段、确认度或文案。
- 前端当前使用 ECharts，不引入新的图表依赖。
- 本地 HeroUI v3 docs 目录缺失，且 `heroui` CLI 当前不可用；实现 UI 时不能凭记忆硬写 HeroUI API。

## Goals / Non-Goals

**Goals:**

- 支持用户输入 ticker 和历史日期，查看该日期的右侧趋势判断。
- 当用户选择非交易日或晚于最新交易日的日期时，返回清晰的有效分析日期。
- 生成默认最近 60 个有效交易日的右侧趋势序列，用于折线图展示确认度、归一化价格、阶段和右侧已触发数量。
- 为历史截面和趋势点提供轻量前瞻结果标签，辅助用户证伪“看起来像右侧”的判断。
- 让趋势图直接暴露确认度与价格的领先/滞后关系。
- 明确总确认度只是结构强度，不是准确率、胜率或上涨概率。
- 强化左侧准备度与右侧触发度的分层表达，避免总分掩盖“底部较充分但右侧未触发”或“强触发但底部结构不足”等差异。
- 保证历史截面计算不读取 as-of 之后的日线数据。
- 让 UI 明确区分“当前分析”和“历史复盘”，并显示请求日期、有效交易日、数据窗口和免责声明。

**Non-Goals:**

- 不做交易策略回测、买卖点收益曲线、策略胜率统计、组合级期望值统计。
- 不根据历史表现自动调参或改变信号阈值。
- 不让前瞻结果标签参与 as-of 当天判断，避免把验证结果变成未来函数。
- 不新增多股票批量对比。
- 不引入新的外部行情数据源。
- 不在本变更中完成 HeroUI 组件迁移。

## Decisions

### D1: 把 as-of 作为报告构建入口参数，而不是新增独立分析引擎

`build_signal_report(ticker, as_of=None, trend_window=60)` 负责统一构建当前报告和历史报告。内部先拉取足够长的日线，再按 `as_of` 截断到有效交易日，随后复用 `compute_all_signals`、`determine_phase`、`generate_narrative` 和 `make_report_payload`。

理由：

- 保持当前分析和历史复盘同源，用户看到的差异只来自数据截面。
- 避免复制一套 signal pipeline，降低公式漂移风险。
- 后续如果信号公式迭代，历史复盘自动使用同版本规则，便于版本化比较。

替代方案：新增 `backtest.py` 独立计算模块。放弃原因是初期会造成两套报告 payload 和两套测试路径，收益不明显。

### D2: 非交易日解析为不晚于请求日期的最近交易日

API 接收 `as_of=YYYY-MM-DD`。如果请求日期不是交易日，系统使用日线数据中 `date <= as_of` 的最后一条作为 `effective_date`，并在 payload 中保留 `requested_as_of`。如果请求日期早于可用数据首日，则返回 400。

理由：

- 用户自然会选择日历日期，不应该要求他们知道交易所休市。
- “有效交易日”显式返回，可以避免误以为周末也有分析。

### D3: 历史复盘中的 quote 不使用实时 quote

当前 `build_signal_report` 会尝试 `get_quotes([ticker])` 获取实时名称、价格和涨跌幅。历史复盘模式下不能用实时价格覆盖历史截面价格，因此：

- `price` 使用 `effective_date` 当天的收盘价。
- `change_pct` 使用相对上一有效交易日收盘价计算。
- `name` 可继续使用 quote 名称，若 quote 获取失败则使用 ticker，但不得使用 quote 价格。

理由：名称不是数值判断输入，实时名称可接受；价格和涨跌幅会误导历史复盘，必须历史化。

### D4: 趋势序列只存摘要点，不重复返回 60 份完整报告

新增 `right_trend` 字段：

```json
{
  "window": 60,
  "points": [
    {
      "date": "2026-06-01",
      "close": 101.2,
      "normalized_close_pct": 37,
      "score_pct": 64,
      "phase": "右侧初步确认",
      "right_score_pct": 71,
      "right_confirmed_count": 3,
      "right_total_count": 5,
      "states": {
        "above_ma": "success",
        "support_retest_hold": "warning"
      },
      "forward_returns": {
        "d5_pct": 2.1,
        "d10_pct": -0.4,
        "d20_pct": 6.8,
        "max_gain_20d_pct": 9.3,
        "max_drawdown_20d_pct": -3.2
      }
    }
  ]
}
```

每个点通过同一套截断计算得到，但只返回图表和 tooltip 必需字段。`forward_returns` 只作为证伪标签展示，不参与该点的信号计算。

理由：

- 60 份完整 signals payload 体积大，前端也不需要。
- 摘要点足够画折线图、阶段标记和 tooltip。
- 如需查看某一天明细，用户可以点击或选择对应日期后重新请求完整历史报告。
- 归一化价格与确认度同轴叠放，能更直接暴露判断是否滞后于价格。

### D5: 趋势计算使用日线窗口循环，成交密集区可降级

60 日序列对每个有效交易日重复调用信号计算。日线相关信号必须严格按截断后的 `df` 计算。成交密集区依赖 5 分钟 K 线，数据源未必支持历史分钟截断；实现时按以下优先级处理：

1. 如果可拿到 as-of 之前的分钟 K 线，则构建对应历史 volume profile。
2. 如果无法保证分钟数据历史截断，则不使用未来分钟 profile，`chip_concentration` 走空 profile 降级路径。
3. payload 的 metadata 标注 `volume_profile_mode`，让用户知道该截面的筹码集中信号是否完整。

理由：宁可缺失部分左侧辅助信号，也不能用未来分钟成交分布污染历史判断。

### D6: 前端趋势图作为证伪镜，日期选择放在查询表单内

页面保留当前 ticker 输入。新增日期输入或日期选择控件，支持清空日期回到当前分析。报告中：

- Hero 区显示当前或历史截面的结论。
- 趋势折线图显示默认近 60 个交易日的 `score_pct` 与 `normalized_close_pct` 叠放线，tooltip 展示 phase、right score、right confirmed count 和前瞻结果标签。
- 历史复盘时显示 `requested_as_of`、`effective_date` 和“仅使用该日前数据”的说明。
- 图表标题和说明使用“证伪/校准/复盘”语义，不使用“预测/胜率/策略收益”语义。

理由：用户先看所选日期结论，再用折线图判断它是否是孤立跳变、持续改善、滞后追认，或被后续走势证伪。

### D7: 前瞻结果标签轻量化，不升级为策略回测

前瞻标签从同一份完整日线中读取 as-of 之后的未来交易日，只计算描述性结果：

- 后 5 / 10 / 20 个交易日涨跌幅。
- 后 20 个交易日内最高涨幅。
- 后 20 个交易日内最大回撤。

这些字段不计算入场成本、出场规则、仓位、胜率、盈亏比或组合收益。

理由：本项目当前定位是辅助判断重点个股，而不是自动交易系统。轻量标签足够提醒用户“这个右侧判断后来是否被价格验证或证伪”，同时避免过早进入样本选择、滑点、仓位和组合统计的复杂度。

### D8: 总分保留为结构强度，报告表达必须分层

现有 payload 已包含 `confirmation.score_pct`、`confirmation.left.score_pct` 和 `confirmation.right.score_pct`。本变更不重写底层加权算法，而是明确展示语义：

- `confirmation.score_pct` = 当前结构强度 / 趋势确认强度。
- `confirmation.left.score_pct` = 左侧准备度，表达底部结构、抛压缓和、波动收敛等准备条件。
- `confirmation.right.score_pct` = 右侧触发度，表达站均线、放量、回踩不破、动量和低点抬升等启动条件。

前端和 narrative 不得把总分描述为“准确率”“胜率”“上涨概率”或“预测概率”。主结论应优先给出分层诊断，例如：

- “左侧准备充分，右侧触发不足，继续观察触发位。”
- “右侧强触发，但左侧筑底不足，属于强启动待回踩确认。”
- “左侧和右侧同时改善，趋势结构较完整。”

理由：统一打分仍有用，它是当前结构强弱的压缩指标；但如果不分层解释，用户会误读成未来正确率。分层表达能保留现有算法的连续性，同时提高诊断可读性。

## Risks / Trade-offs

- **[计算耗时增加]** → 60 日序列会重复计算信号；后端复用已拉取的日线 DataFrame，`trend_window` 做上限约束，避免重复拉行情。
- **[成交密集区历史分钟数据不可得]** → 降级为空 profile 并标注 metadata，不用未来数据兜底。
- **[历史规则版本变化]** → 复盘反映“当前版本规则在历史数据上的判断”，不是当时版本系统的真实输出；payload 增加 `analysis_version` 或 `rules_version` 预留字段。
- **[非交易日用户困惑]** → 同时展示请求日期和有效交易日，并在 API 中返回解析原因。
- **[前瞻标签被误读为预测或策略收益]** → 文案使用“证伪/复盘/后续走势标签”，避免“预测/胜率/收益曲线”等措辞，并明确标签不参与当日判断。
- **[总确认度被误读为准确率]** → UI 和 narrative 使用“结构强度/确认强度”语义，并展示左侧准备度与右侧触发度解释。

## Migration Plan

1. 增加 `as_of` 日期解析和日线截断 helper，覆盖交易日、非交易日、越界日期。
2. 扩展 `build_signal_report` 参数和 payload metadata，保持无 `as_of` 时现有行为兼容。
3. 增加 60 日 `right_trend` 序列构建，复用已截断的日线窗口。
4. 扩展 `pipeline/server.py` 解析 `as_of` 和 `trend_window` 查询参数。
5. 扩展前端 API/types/App 表单状态。
6. 在 `SignalTrendReport` 中加入历史复盘 metadata、分层解释、右侧趋势证伪镜折线图和前瞻结果 tooltip。
7. 添加后端单元测试、API 测试和前端构建验证。

回滚：保留 `build_signal_report(ticker)` 默认路径，移除或忽略 `as_of` 参数即可回到当前分析模式；前端隐藏日期输入和趋势图不影响原有报告接口核心字段。
